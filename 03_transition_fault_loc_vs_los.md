## What you will build
Stuck-at tests catch wires stuck at a value. Modern chips also fail because gates are **too slow**. These are **delay defects**, modelled as **transition faults** (slow-to-rise, slow-to-fall). You will generate transition patterns two ways and compare:

- **LOC** (Launch-On-Capture, also called broadside)
- **LOS** (Launch-On-Shift, also called skewed-load)

Result: a table showing coverage, pattern count and the practical tradeoffs. This shows you understand real production test.

## Concepts (the part interviewers ask)

A delay test needs **two clock cycles at functional speed**: one to *launch* a transition, one to *capture* the result.

```
shift in pattern (slow clock, SE=1)
      |
  LAUNCH pulse  ---- one functional period ---- CAPTURE pulse   (fast clock)
      |
shift out response (slow clock, SE=1)
```

| | **LOC** | **LOS** |
|---|---|---|
| How the transition is launched | A normal capture cycle computes the next state, which launches it | The last shift cycle itself launches it |
| Scan enable (SE) | Goes low *before* launch; SE can be slow | SE must switch from 1 to 0 **between launch and capture, at speed** |
| Coverage | Lower (second vector is a *function* of the first, so some pairs are impossible) | Higher (second vector is just a one-bit shift, so more freedom) |
| Pattern count | Higher | Lower |
| Hardware cost | Easy | SE becomes a timing-critical net; needs pipelined or buffered SE |
| Risk | Over-testing is low | Can test paths that are never functional (yield loss) |

Key phrase: **LOC trades coverage for easy implementation; LOS trades implementation pain for coverage.**

## Step 2: Create two test modes
A test mode describes how the tester operates the chip. You need one for LOC and one for LOS, each with a launch-capture clock sequence.

```bash
build_testmode -testmode TDF_LOC -assignfile top_loc.pinassign -modelname top -workdir ./tbdata
build_testmode -testmode TDF_LOS -assignfile top_los.pinassign -modelname top -workdir ./tbdata
```
**(verify)** The difference between the two modes lives in how the sequence of clock pulses and scan-enable transitions is defined. Check the Modus docs for the dynamic-test option names (look for keywords like *dynamic*, *launch*, *capture*, *LOS*, *LOC*, *sequence definition*). Document exactly what you configured.

Run structure checks on each:

## Step 3: Build the transition fault list
```bash
build_faultmodel -fullfault yes -includedynamic yes -workdir ./tbdata
```
**(verify)** The switch that enables dynamic (transition) faults can be named differently by version. Look at `build_faultmodel -help`. After it runs, the log should list **static** and **dynamic** fault counts separately. Transition faults are about **2 per gate pin**, the same count as stuck-at.

## Step 4: Generate patterns for each mode
```bash
create_logic_tests -testmode TDF_LOC -experiment loc_exp -workdir ./tbdata
commit_tests       -testmode TDF_LOC -inexperiment loc_exp -workdir ./tbdata

create_logic_tests -testmode TDF_LOS -experiment los_exp -workdir ./tbdata
commit_tests       -testmode TDF_LOS -inexperiment los_exp -workdir ./tbdata
```
Make sure the run targets **dynamic** faults, not stuck-at. **(verify)** The option name that selects the fault type may be `-faulttype`/`-fault_type` or may follow from the test mode; read the log header to confirm it says transition/dynamic faults.

## Troubleshooting
| Problem | Fix |
|---------|-----|
| Dynamic fault count is 0 | The fault model was built without dynamic faults; check `build_faultmodel` options |
| Very low LOC coverage | Reset or clock is not held in capture; check DRC output; or too many multi-cycle or false paths |
| LOS DRC error on scan enable | SE not defined as at-speed-switching; check LOS mode definition |
| Coverage is identical for LOC and LOS | Both modes are really running the same sequence; re-check sequence definition |
